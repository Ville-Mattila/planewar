## A-116 (CQ-5) The four accessors get 04 s3.7 rows: `overlay`, `cargo`, `cargo_kind` are not replicated in v1; `link` has its ship / pad ends from `DOCKED` / `LAUNCHED` and `TEAM_DETAIL` pads

**Evidence.**

1. **04 s5.6 (04:709) promises a row per accessor and 04 s3.7 (04:437-456) lacks four.** The table already has the form for a non-replicated accessor (`path_grid_version`: "not replicated (server AI only) | always (returns 0)"), so "no row" and "not replicated" are different states; the review is right that the table must say which.
2. **`overlay`** (03 s3.2 row 35; R0 B.3: NONE, SAFETY, RECOVER_CEILING, LINK_BRIDGE) is "set by `ControlMachine`, executed by `sim_ai`": server-side execution state. Its player-facing signals already travel: `ALERT(LINK_WEAK)` once on entering `LINK_BRIDGE` (05 s2.3 C13, 06 s7.1 alerts row), `RELEASED(reason)` on every release path, `CEILING_RELEASE`, and the own-team `ai_tag` (A-94, UX-43 HUD labels). No 06 HUD element reads `overlay`; the one client that could observe `LINK_BRIDGE` on its own unit is the one whose input is not arriving. NET-18's prediction does not read it (04 s5.2 names no overlay; a bridged unit is flown by the server). A pilot-block byte would cost 1 B per tick for a value the HUD never shows.
3. **`cargo` / `cargo_kind`** (03 rows 29-30). 06 s7's consumables row (06:568) reads `hp01`, `fuel01`, `ammo`, `bombs`, `rockets`; no 06 panel reads cargo. The boolean the client does need ("loaded" = Ice cargo or towing, 02:138, `tow_turn_rate_mult`; the Hauler's visual state) is already wire flags bit 6 "shield up / cargo loaded / towing (per def class)" (04 s3.3). The amount is a HUD nicety for a possessed Hauler / Harvester with no consumer yet; the cheapest path when one appears is an appended pilot-block field (NET-39's title already says "pilot block additions").
4. **`link`** (03 row 31) has three meanings: the pad a ship is docked on / the ship a pad services; the Extractor's Refinery; the wreck's towing ship while TETHERED (A-104). The ship / pad pair travels today: `DOCKED (ship u16, pad u16)` and `LAUNCHED (ship u16, pad u16)` are roster-scoped events (04 s3.6 rows 4, 6), and `TEAM_DETAIL` pads carry `occupant` for the own team (04 s3.7 `pad_occupant`); the hole is a pair docked before the client's roster held them with the pad not in the own-team pads (an enemy ship docked when the client joined): the KEYFRAME FULL record has flags bit 2 only. The tow end has **no** source: `WRECK_SPAWNED` / `WRECK_SALVAGED` / `SALVAGE_DELIVERED` do not carry the pair and `Salvage.try_attach` emits no event (`sim/salvage/MODULE.md` W6). The client that needs the pair is presentation: `vfx_tether` "from the Hauler's `HP_Tether` to the towed wreck" (07 s6, ART-17). The Extractor -> Refinery end has no client consumer.
5. **The rest of the table.** `alive`, `def_id`, `owner`, `team`, `def_kind`, `radius`, `flags`, the live lists, `visible_to`, `ids_in_cell` / `ids_near` / `read_poses` also had no row while NET-17 implements them from the roster, `ENTITY_META`, the defs and the sampled mirror (04 s3.1, s3.6, A-112, A-114). They get one row so the s5.6 sentence is true.

ART-17 gains a note.

## A-117 `NetSimView.unknown(id)` covers replicated accessors only; `field_unknown(id, accessor)` is the HUD's per-field query

**Evidence.**

1. 04 s5.6 (04:709): "Fields a client does not receive for an entity ... are flagged `unknown` in a parallel bitset the HUD may consult." 04 s3.7 (04:435): "Fields a client does not receive for an entity return the def default and set the entity's bit in the `unknown` bitset." Read literally with a never-carried accessor, every entity's bit is set forever: PR #118 does exactly that (`net_sim_view.gd:96-99`: `unknown(id)` is true while `NetUnknown.NEVER` is non-empty), documents it (CS8) and pins it. The sentence was written when every `SimView` accessor had a wire source; A-116 now rules four not replicated and 04 s3.7 already had `path_grid_version`, so the literal reading makes the bit carry zero information.
2. **NET-39's acceptance** (04 `team_detail_test`: "own-team values exact ..., other teams flagged `unknown`") is a statement about the per-entity bit and requires the own-team bit to be clear. With the literal reading it can never pass.
3. 04 s3.7's "Unknown when" column is per accessor and per entity; `field_unknown(id, accessor)` (`net/client/MODULE.md:54`, `NetUnknown.field`) is that column as code. The per-entity bit is its OR over some set of accessors; the only question is the set.
4. Rows whose decoder has not landed yet (NET-39's `TEAM_DETAIL` rows, GD-38 `shield01`, GD-41 `wreck_ore`, `landing_grade_last` until the `LANDING` routing) are temporarily "not received for every entity". Including them in the bit reproduces the always-true problem until M4; excluding them permanently loses the other-team signal NET-39 needs. They are a separate, shrinking set.

**Decision.** `unknown(id)` is **true when any accessor with a 04 s3.7 wire source that the current protocol carries for some entity is not received for `id`**. Two sets never set the per-entity bit: (1) **NEVER** = the rows 04 s3.7 marks not replicated (`path_grid_version`, `overlay`, `cargo`, `cargo_kind`, the tow / Extractor ends of `link`); (2) **PENDING** = rows whose source message is not yet decoded by the client (today: the `TEAM_DETAIL` rows of NET-39, `shield01` GD-38, `wreck_ore` GD-41, `landing_grade_last`, `flags`' uncarried bits); a PENDING row joins the bit in the PR that lands its decoder. Both sets are `field_unknown` true for every entity. Consequences: the own possessed unit in tier A is **not** unknown; an own-team tier-A ship is not unknown; a C-tier blip is unknown (`basis`, `vel`); an other-team entity is unknown once NET-39 lands (its `TEAM_DETAIL` rows), which is the `team_detail_test` sentence; a split wreck is unknown (`radius`, A-114). **`field_unknown(id, accessor)` is the HUD's per-field query** and 04 s5.6 names it. **Code: NET-39** (owner of "NetSimView accessors of 04 s3.7 with the unknown bit"): `NetUnknown.NEVER` split into `NEVER` and `PENDING`, `unknown(id)` drops the `not NEVER.is_empty()` term, `test_net_sim_view.gd` asserts `unknown(own) == false`, `unknown(own-team A ship) == false`, `unknown(C blip) == true`, `unknown(other-team entity) == true` after `TEAM_DETAIL`, and `net/client/MODULE.md` CS8 is rewritten. PR #118 keeps its current behaviour and tests (documented in CS8 as the interim; not a blocker, as the review says). **OWNER (default applied): NET-39, not a separate task.** The alternative is a 0.25 d Haiku net task right after NET-17 so the semantics land in M3; nothing in M3 reads the per-entity bit (every HUD task runs on `LocalSimView` until NET-39), so the default is the cheaper one.

**Not accepted:** removing `unknown(id)` (NET-39's acceptance and 04 s5.6 both use the per-entity form; the HUD's faint-outline cue of 04 s5.6 wants one bit per entity); making the bit "any `field_unknown`" (evidence 1); a per-accessor bitset in the `SimView` base class (`LocalSimView` would carry dead API; `field_unknown` is `NetSimView`-only and `ui` reaches it through `SimView` only when it holds a `NetSimView`, which the HUD may test with `is`).

## A-118 (AI-17 review contract question 1 and Q4) The tower slew law GD-09 implements

**Evidence.**

1. 02 s4.4 (02:258): "`turret_turn_dps` limits slew. A possessed tower slews with the `pitch`/`yaw` input axes as rates." 05 s1.1 (05:57), 04 s2.4 (04:199), R0 C2-09 and B.3: towers read `pitch` / `yaw` as slew rates and `FIRE1`; no aim bytes. 03 s4.1 step 5: "turret slew for towers". 03 s3.2 rows 10-11: `fwd`, `up` stored for every kind, `right = fwd.cross(up)` derived. Nothing else is written down, which is why AI-17 built a stand-in (`Ai17Kit.SlewDriver`) and the review asks for the contract before GD-09 builds the real one.
2. **One def value.** `towers.json` carries `turret_turn_dps` only (120 / 60 / 90 / 30); there is no per-axis rate and no `rate_accel` for towers (ships have `pitch_rate_dps`, `yaw_rate_dps`, `roll_rate_dps`, `rate_accel_dps2`, `Kinematics._stick_tick`). ADR-09 (01:528): no sim constant outside a def, so a second rate or an acceleration cannot be invented in code; a new def key is a B.1 change that no doc asks for.
3. **A possessed tower is a player control** (02 s4.4; 06 s3 input maps). With body-axis slew the mount rolls off the site vertical over time (the review's observation); a player steering a turret expects "yaw turns level, pitch raises the barrel", which is an azimuth / elevation mount. The site normal is `pos.normalized()` (01 s3.1.3 datum; the structure's spawn `up`).
4. **Fire gates are sim rules** (02 s4.4 missile lock, flip-break window, power; 05 s6.8 last line "Power < 100 % scales fire rate (sim); power < 50 % -> towers offline (sim)"; 05 s2.3 possession table: an offline tower "slews but cannot fire (sim rule)"). "Possessed towers ignore all of this" (05 s6.8) refers to the brain's target choice, not the gates.
5. **Q4** (first-pass candidate scan uncapped): TC2 bounds the second pass by `max_candidates`; towers are in no 05 s10 governor rung; no session wires towers yet; the row is a fleet mean. The reviewer recommends deciding at AI-30 with a measurement; AI-30 is the governor and perf benchmark task (05 s10) and depends on AI-17.

**Decision (binding for GD-09; 02 s4.4 and 05 s6.8 gain the sentence; `sim/MODULE.md` and `sim/steer/MODULE.md` follow in GD-09 / AI-44).**

- **(a) Cap on the norm.** The commanded pair `(pitch, yaw)` is clamped to **unit norm** before scaling by `turret_turn_dps`, so the mount's axis-rate magnitude never exceeds `turret_turn_dps`; a diagonal command moves at the cap, not sqrt(2) x it. One def value, one cap.
- **(b) Azimuth about the site normal, elevation about the turret's right.** `n = pos.normalized()`; `right = fwd.cross(up)`. Azimuth rotates `fwd` and `up` about `n` (positive `yaw` = muzzle left, the ship convention of `sim/MODULE.md` "yaw + nose left"); elevation rotates them about `right` (positive `pitch` = muzzle up). Starting from the spawn basis (`up` = `n`), `right` stays tangent to the site forever, so the turret never rolls. **The pole:** an elevation step that would take |elevation| to or past 90 deg is truncated at the pole (a geometric limit of the mount, no def key; the `h_rel` envelope bounds what is engaged).
- **(c) No rate dynamics.** The commanded rate applies in full in the tick it is commanded (step 5), before step 9 fire; no `rate_accel` for towers. The dead-beat law of `TurretAim` (TA1) then arrives in one tick without overshoot. A possessed tower feels instant; smoothing a human's stick is the client's assist stack (UX-07), not the sim.
- **(d) The muzzle is `store.fwd`.** `up` is re-orthonormalised against `fwd` after each slew tick with `right` kept tangent (`up = right.cross(fwd)` normalised, `right` from `n`).
- **(e) The sim alone enforces, at fire time and for AI and possessed towers alike:** `target_kinds`, the [`h_rel_min`, `h_rel_max`] band, `target_agl_min` and the datum-horizon test for lock, `lock_time_s` continuous lock, the 100-500 m flip lock-break, power < 50 % no fire (slew allowed), the fire cone (`in_fire_cone`), ammo / supply draw (GD-36). The brain and a human only steer and press `FIRE1`.
- **`TurretAim` must change** (az / el undershoots by cos(elevation) in azimuth): **AI-44** (sim/steer+sim_ai, Sonnet, 0.25 d, M3, after AI-17): `TurretAim.slew` takes the site normal `n` (appended argument), commands elevation from the error's `right` component and azimuth from its `n` component divided by cos(elevation) (guarded at the pole), clamps the pair on the norm, and `Ai17Kit.SlewDriver` adopts the same law (az / el, norm clamp, no lag) so SC-30 / SC-31 run against the contract until GD-09 removes the stand-in. The orchestrator may fold AI-44 into AI-17's round 2; AI-44 then closes as done there.
- **GD-09** gains the acceptance below, `depends_on` AI-17 and AI-44, and re-runs SC-30 / SC-31 against the real slew with `Ai17Kit.SlewDriver` / `SlewSink` deleted.
- **Q4:** no first-pass cap before AI-30. **AI-30** adds a raid-over-a-base case (about 20 towers, 30 enemy ships inside range) to `ai_tick` and a tower scenario to the TEST-04 A/B, and decides from the numbers whether the tower brain needs a first-pass candidate cap (for example nearest K by the `near_built` distance); if yes it files a sim_ai follow-up, if no it records the measurement.

**Not accepted:** per-axis caps (needs a second def value or sqrt(2) diagonals); body-axis slew (rolls the mount; a possessed tower's yaw would stop being level); a `rate_accel` lag (a def key no doc asks for, and the dead-beat law then overshoots); elevation limits as def keys (no 02 row; the envelope already bounds engagement); client-side fire gates for possessed towers (01 ADR-07, 04 s3.6: never predict weapon hits; the sim validates fire).
