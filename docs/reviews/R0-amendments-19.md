## A-128 (Q1) C-06 is GD-26's, not GD-09's; the 02 s18.3 band stays; GD-34 owns the retune if the band is unreachable by data

**Evidence.**

1. **C-06 is a balance sweep, the other four are rule tests.** 02 s18.3 (02:1175-1180): C-01..C-04 each assert one 02 s4.4 rule (envelope, floor, AGL lock floor, flip window) deterministically; C-06 asserts a *survival rate over 50 seeds* against the Flak's 02 s4.1 / s4.2 anchors (`flak_gun` 30 x 2 every 2 s, `spread_deg` 0.5, `flak_shell` 25 m burst at 300 m/s with the 0.3 s `fuse_delay_s`) and the Bomber's (`hp` 300, cruise speed). GD-09's acceptance (02:1259, 09 s3.3) lists it with the rule tests only because both touch Flak; 09 s3.3 already gives C-06 to GD-26 with a Sonnet tier ("Sonnet for C-06, C-08"), i.e. the plan expected it to be the harder, balance-flavoured one.
2. **The PR's two harnesses show the band is not a GD-09 code property.** (a) A constant-velocity Bomber against the 02 s4.4 straight-line intercept is a deterministic hit: 0.5 deg of spread is 8.7 m at 1,000 m against a 25 m burst radius, so every salvo lands and 300 HP falls in five salvos (10 s) while the Bomber spends about 30 s inside 1,500 m. No envelope, slew or lock rule in GD-09 changes that; only the anchors (spread, burst radius, fuse delay, damage, Bomber HP / speed) or a design mechanism the docs do not have (flak dispersion growing with range, a timing error, a Bomber evade policy) do. 02 s11.2 fixes the autopilot Bomber as "releases level at standard speed and heading", so the real brain *is* the straight-line case over the run. (b) The real-brain harness released 12/12 because the defender saw the Bomber at about 600 m. `towers.json` gives every tower `sensor_radius` 1,600 (02 s5.2 table, 02:305-307) and 03 s3.7 counts every structure as a sensor; a Flak that sees a Bomber at 600 m rel only when 600 m away is either the harness (the Flak unfinished / not the sensor the test thinks it is, the Refinery's 600 m being the only sensor) or a Vision finding, and in neither case GD-09's.
3. **Blocking a 2-day PR with 2,000+ green tests on a balance band is the wrong trade** (10 s3.3: acceptance by named tests *or a REPORT*; the PR body is that report). A failing or loosened C-06 in GD-09 would hide the real question, which is a 02 anchor question (GD-34, "Balance pass 1 ... retune anchors, revise 02", Opus).

**Decision (OWNER; default applied).**

- **GD-09's acceptance** reads "C-01, C-02, C-03, C-04 pass (Opus review); C-06 is GD-26's (R0 B.25 A-128)". 02 s19's GD-09 row and 09 s3.3 are patched to match. The PR's C-06 section stands as the report.
- **GD-26 (Sonnet part)** builds C-06 as 02 s18.3 writes it, on the real `BomberBrain` ATTACK against a Refinery guarded by one, then two, finished and supplied `flak_battery` of the defending team at 600 m rel, 50 fixed seeds each, in `godot/test/sim/balance/`. Before measuring it asserts the preconditions that PR #132's harness (b) did not: the Flak is finished, powered and supplied, the defending team has `visible_to` on the Bomber by the Flak's own `sensor_radius` (first visible at >= 1,500 m from the Flak), and the Bomber enters `range_m` with bombs aboard. A precondition failure is a **BUG-n task against the owning lane** (Vision, Build or the brain), not a C-06 result.
- **If the preconditions hold and the band (>= 60 % survive with one Flak, >= 80 % die before release with two) is met**, C-06 is green and nothing else moves. **If it is not met**, GD-26 commits the test with its band read from the scenario JSON (`godot/test/sim/scenarios/c06_bomber_vs_flak.json`: `one_flak_survive_min`, `two_flak_die_min`) set to the *measured* rates minus 10 points as a regression floor, records the measured rates in the PR body and in the 02 s18.3 C-06 row as "measured a / b %, band open: GD-34", and GD-26 is still done (its acceptance is "run on every PR in < 2 min", not the band).
- **GD-34 then owns the band** (acceptance_append): make 02 s18.3 C-06 reachable by data alone within the +-15 % anchor latitude (`flak_gun.spread_deg`, `flak_shell.blast_radius_m`, `fuse_delay_s`, `flak_gun.damage_min/max`, Bomber `hp` / `v_cruise`), or, if the sweep shows the straight-line intercept cannot miss a constant-velocity target inside that latitude, file the design change as a contract question (a range-scaled flak dispersion or a brain-side Bomber evade would be new 02 text and a 05 policy: Architect + owner, 10 s4.1 "Change"), and restore the JSON band to 60 / 80 when it passes. The band numbers in 02 s18.3 do not change here.

**Not accepted:** keeping C-06 in GD-09 (a tower-rule task cannot reach a balance band); amending the band now (no measurement under valid preconditions exists yet; the PR's 0/50 came from a Bomber with the brain removed and the 12/12 from a defender that did not see); a C-06 that counts "released" without "survived" or vice versa (02 s18.3 asserts both legs).

## A-129 (Q2) A-118 (e) is the strict form: a tower round spawns only while the tower holds an envelope target; the target is refreshed once per fire window, never per shot

**Evidence.**

1. **The text is unambiguous.** 02 s4.4 Aim bullet (02:258): "every fire gate of this section (envelope, `target_agl_min`, horizon, `lock_time_s`, flip lock-break, power) is applied by the sim at fire time for AI and possessed towers alike"; A-118 (e): "the sim alone enforces at fire time, AI and possessed alike: `target_kinds`, [`h_rel_min`, `h_rel_max`], `target_agl_min` + horizon for lock, ..."; 02 s10.3 (02:787): "Autocannon: High **no**", and the design statement "there is no safe altitude over a mixed defence" depends on the Autocannon's ceiling being real for a human gunner too. 05 s6.8 (05:655): "Possessed towers ignore all of this" refers to the brain's idle / power handling, and 05 s2.5 (05:249) says a possessed offline tower "slews but cannot fire (sim rule)": the possessed tower is already sim-gated for power; the envelope is the same kind of gate. As built (review), a possessed Autocannon shoots a Bomber at 600 m rel and C-01 / C-02 pass only through `TowerBrain.eligible`, which ADR-07 (01 s7, server authority) and A-118's "not accepted: client-side fire gates" rule out as the enforcement point.
2. **The cost objection is answered by the fire cadence, not by dropping the gate.** Tower weapons fire in windows: `gun_turret` 5 rounds per 1.2 s burst window, `flak_gun` a 2-round salvo every 2.0 s reload, `rail_gun` 1 round per 8 s, `rocket_tower` after `lock_time_s` 1.0 (02 s4.1). `WeaponFire` already runs `SeekerScan.pick` (the envelope-aware candidate scan since PR #132) for every lock weapon every tick and for the flak fuse at every shot (CB14), so the flak already pays the scan the stricter form needs. One scan per tower per *window* for guns and rails (16 Autocannons / 1.2 s + 12 Rail Lances / 8 s per player at the 02 s5.2 caps) is below one scan per tick for the whole tower population; `TowerBrain` thinks at 3 Hz on the same candidates.
3. **No new state.** `lock_target[s]` / `lock_time[s]` are per main-range slot (one per entity, serialised, `sim/combat/MODULE.md`); towers with a gun / flak / rail weapon leave them at 0 today. Holding the window's target there costs no `FORMAT` change and S4 holds (the scan is a function of state; the window boundary is the existing cooldown).

**Decision (binding; GD-09 round 2).**

- **CB13a (tower fire gate).** A tower's gun / flak / rail round spawns only if `lock_target[s] != 0` *and* that target is still alive, hostile, of the tower's `target_kinds`, inside `range_m` and inside the envelope (`SeekerScan.in_envelope`; the re-check is one entity, O(1)). The round still flies along the muzzle (`store.fwd`): a possessed gunner leads, baits or misses by hand (02 s11.2 Towers row); the sim only refuses to shoot while nothing engageable exists. Towers with no eligible target spend no ammo, draw no supply and emit no `PROJECTILE_BATCH` (CB11 unchanged).
- **Refresh cadence.** `lock_target[s]` of a gun / flak / rail tower is set by the existing `_pick` (envelope, `target_kinds`, range, horizon; `lock_cone_deg` 0 / 360 = any direction for these weapons, as CB13 reads it) **when the weapon's fire window opens** (burst window reopens, reload completes, or the first round after a hold with the trigger pressed) and when the held target dies, leaves range or leaves the envelope at a shot (the O(1) re-check fails, so the next shot of the window re-picks once). Never more than one scan per tower per window plus one per failed re-check; **no per-shot scan**. The flak fuse target (CB14) and the gate target are the same pick, so the flak pays nothing new. The AI's `TowerBrain` continues to choose *where to aim* among team-visible candidates (05 s6.8); the sim's held target is the fire permission, not the aim.
- **No visibility term.** CB13 has none today and 02 s4.4 names none; a possessed gunner shooting at a muzzle-pointed, in-envelope hostile the team cannot see is allowed (the shot reveals nothing; Vision is 03 s3.7's). Vision fairness stays the brain's (05 s6.8 "team-visible").
- **Rockets:** unchanged (CB13 lock as built, with the envelope in the pick since PR #132).
- **Tests (GD-09 round 2, named in `test_tower_gates.gd` or `test_c_tower_scenarios.gd`):** a possessed Autocannon with FIRE1 held and its muzzle on a Bomber at 600 m rel for 20 s spends 0 rounds and emits no `PROJECTILE_BATCH`, while the same tower with the Bomber at 300 m rel fires on the first burst; a possessed Flak with FIRE1 held on a Dart at 100 m rel spends 0 shells; a possessed Rail Lance with FIRE1 held and no hostile in range spends 0 rounds; the C-01 / C-02 scenarios pass with `TowerBrain.eligible` forced true for the test (so the sim, not the brain, is shown to refuse); a Bomber leaving the envelope mid-burst stops the burst at the next round and the tower re-picks once; `test_weapon_fire.gd` tower rows gain a hostile in the envelope where they relied on firing at nothing; S4 byte-exact restore mid-window holds (`lock_target` already serialised). Perf: `test_tower_perf.gd` or the `perf_tick.gd` row 9 delta with 32 firing towers, cited in the PR body.
- **MODULE.md:** `sim/combat/MODULE.md` CB13a as above; 02 s4.4 Aim bullet gains the sentence (patched here).

**Not accepted:** the lax form as built (a client-reachable fire path that ignores the envelope contradicts 02 s4.4, A-118 (e) and ADR-07; the brain is not an enforcement point); a per-shot O(entities) scan (the review's cost objection; the window cadence gives the same guarantee); a muzzle-ray hit test as the gate (a straight-line intercept leads the target, so the muzzle never points at it); a new `fire_gate_hz` def key (ADR-09 governs sim values, and the cadence is the weapon's own window; no new number).

## A-131 (Q4) In-flight AGL lock loss applies to ships in flight only

**Evidence.** 02 s4.4 (02:261): "A rocket in flight loses lock permanently if its target drops below 40 m AGL", written in the Missile Tower row's "ground clutter" sense (02:255, 02:787 "Deck, below 40 m AGL: no lock"), i.e. about a *flying* target hugging the ground. The Missile Tower's `target_kinds` is `["ship"]`, so for its rockets the question never arises; the Lancer's `rocket_lancer` fires the same `rocket` projectile at ground units and structures (02 s4.1 `ground_mult` 1.0, `structure_mult` 1.0; 02 s10.4 "Lancer vs Autocannon: rockets 1,500 m out-range"), which sit at AGL 0 by definition, and a landed or docked ship is a target at rest on a pad. Reading the rule literally would make every Lancer rocket at a Harvester, a tower or a parked ship go blind at launch, which `test_lancer_brain` caught and which contradicts 02 s10.4's Lancer standoff. The flip clause is unaffected (only a ship flips).

**Decision.** Ratified as built (`sim/world/MODULE.md` W8): the AGL clause applies when the target is a ship (`EntityStore.K_SHIP`) that is not `LANDED` (a DOCKED ship is landed); ground units, structures and landed or docked ships never lose a rocket to the AGL clause; the flip clause applies to any ship target that starts a flip inside the window. 02 s4.4 gains "(a ship in flight; ground units, structures and landed ships are not 'below AGL')". The tower-side `target_agl_min` lock gate is unchanged (towers that carry it engage ships only).

**Not accepted:** applying the clause to every target kind (the Lancer's ground role dies); a per-kind def switch (nothing in 02 asks for one; the "flying ship" reading is the only one that keeps 02 s4.4 and s10.4 consistent).

## A-132 (NET-58 a) A projectile's `ROSTER_REMOVE` follows its death or exit from `V` by 3 ticks and its index is not re-admitted for 6 ticks; a 04 s4.1 rule, code constants, no def field

**Evidence.** (1) A-20 (owner-decided): projectile slots quarantine **0 ticks**, so a slot freed in tick t can be another team's rocket in tick t + 1; A-112 makes the roster index a pure function of the slot, so the *index* is reused as fast. (2) SNAPSHOT (channel 2, unreliable) and `ENTITY_META` / `ROSTER_REMOVE` (channel 3, reliable ordered) are independent channels (04 s2.2); a snapshot record for the new occupant can arrive before its META and be parsed against the old entry's team (the own-team `ai_tag` byte, 04 s2.3), and an early REMOVE strands a held record into the NET-05 1 s timeout and a `ROSTER_GAP` keyframe. The PR measures exactly that: 1-3 malformed snapshots per client under TARGET and one `ROSTER_GAP` per client under BAD without the hold, 0 / 0 with it, over 900 ticks and three `ClientSession`s on `LocalTransport`. (3) A-112's "`ROSTER_REMOVE` on death, no 30 s ghost" was written against the 30 s ghost of 04 s4.1 (a Commander-view last-known marker); a 100 ms bookkeeping delay that no view shows is not a ghost. (4) 04 s4.1 already carries two prose timing constants of this kind (the 15-tick tier hysteresis, the 30 s ghost) that live as `net/interest` constants; ADR-09 (01:528) governs *sim-affecting* values, and a roster delay changes no sim outcome, so a defs JSON home would be a category error (`rules.json` is the sim's).

**Decision.** 04 s4.1's projectile paragraph gains: "A replicated projectile's `ROSTER_REMOVE` (reason DEATH or LEFT_INTEREST) is sent **3 ticks** after the death or the exit from `V`, and its roster index is neither listed nor re-admitted for **6 ticks** after that event, so a snapshot that overtakes the next occupant's `ENTITY_META` never decodes against a stale entry and no held record is stranded (A-20's 0-tick quarantine makes the index reusable at once). The hold is roster bookkeeping only: the client's `NetSimView.alive(id)` for the dead projectile is false from the first tick with no record for it, and nothing renders it." Constants `ProjectileMembers.HOLD_TICKS = 3` and the 6-tick re-admission bound (the PR's names) carry doc comments citing 04 s4.1 and this row; `test_projectile_interest.gd` keeps the LocalTransport TARGET / BAD 0-malformed, 0-gap assertions as the contract test. The A-112 row's "on death" reads "on death, within the A-132 hold". The hold must stay below the NET-05 held-record timeout (1 s); a change to it is a one-row amendment. OWNER (default applied).

**Not accepted:** removing the `ai_tag` byte from projectile-block records (a wire layout change and a `PROTOCOL_VERSION` bump for a bookkeeping problem); a def field in `rules.json` or a new `net.json` (not sim-affecting; 04 s4.1's other timing constants are prose + code); a 1-tick quarantine in the sim (A-20 is owner-decided and measured: 44 failed allocs at the cap).

## A-133 (NET-58 b, CQ-6) `SimView.def_id / owner / team / radius` resolve projectile ids on both views; `def_kind` returns -1 for a projectile on both; GD-45 aligns `LocalSimView` and adds the TEST-02 clause

**Evidence.** A-112 names the `NetSimView` accessors that "resolve projectile ids through the block" (`alive / pos / vel / basis / def_id / owner / team / radius / def_kind / read_poses / ids_in_cell / ids_near / projectiles_near`) with META `def_id` = the `ProjectileDef` id (`ContentDB.projectile_index`, A-1) and `owner` / `team` = the shooter's. `LocalSimView` (`sim/local_sim_view.gd:47-176`) resolves `alive` through `ProjectileStore` since A-20 but `def_id / owner / team / radius / def_kind` read `EntityStore` only, returning -1 / -1 / -1 / 0.0 / -1 for a live rocket. `ProjectileStore` already holds `projectile_def`, `owner`, `team` (by shooter at spawn) and the def gives `radius_m`, so the local answer costs one branch on `EntityId.is_projectile(id)`. TEST-02's `simview_contract.gd` is the shared contract (04 s5.6: one test, two views) and has no rocket clause for the four, which is how the gap went unnoticed; 06's rocket-lock warning and `presentation`'s projectile meshes read `def_id` / `team` of `projectiles_near` ids and must get the same answer offline and online.

**Decision.** **Canonical (both views, same inputs, same answer):** for a live replicated projectile id, `def_id` = its `ProjectileDef` id (`projectile_index` range, A-1), `owner` / `team` = the shooter's at spawn (the `ProjectileStore` columns; unchanged if the shooter later dies or is possessed), `radius` = the def's `radius_m`, `alive` as today; **`def_kind` = -1** (there is no `EntityStore.K_*` for a projectile and the kind list is frozen; `EntityId.is_projectile(id)` is the discriminator, `projectiles_near` the enumerator).
