## A-50 (TA-18) `PlayerKind`: ordinals only, no global holder; D1 learns qualified names

**Context.** R0 B.3 lists `PlayerKind: 0 HUMAN, 1 BOT, 2 OPEN` among the frozen enumerations and `sim/MODULE.md` carried `class_name PlayerKind [planned]` as an enum holder. `net/protocol.gd` already defines `enum PlayerKind` inside `Protocol` for the `WELCOME` wire (04). **Decision.** (1) The sim builds **no `PlayerKind` holder**. (2) **D1 fix (tools, TA-53):** a qualified token `Foo.Bar` is a reference to `Foo` only; `Bar` is never resolved as a global class. This is a false-positive repair of the scanner, not a new edge or named type, so `deps.json` is untouched; `tools/tests/test_rules.py` gains the fixture (a `net` file naming `Protocol.PlayerKind` passes; a `net` file naming a bare sim-only class still fails).

## A-52 (TA-14) Hash ring coverage is ~94 m, not 139 m (03 s2.7, s3.6, s6.1)

**Decision.** Erratum applied. 139 m is the corner cell's edge length; the width of an equal-angle strip is smallest at the middle of a face edge, `asin(sin(delta) / sqrt(2))` = 104.1 m of datum arc for `delta = (pi / 2) / 64`, and the 3D radius at `R + RELIEF_MIN` less the `(N - 1) / N` margin gives **ring 1 ~94 m, ring 2 ~188 m** (`Spatial.ring1_m` / `ring2_m`; proof in `spatial.gd`, brute-force coverage in `test_spatial.gd`). `ids_near` takes ring 2 above 94 m, so nothing was missed. Projectile sweeps (<= 50 m per tick at 1,500 m/s plus both radii) stay in ring 1 while the largest hashed radius is under ~43 m; a future def with a larger radius makes `Collision` take ring 2, not a doc change. 03 s2.7, s3.6 and s6.1 now say so.

## A-53 (TA-14 -> TA-19) Pad approach column is exempt from ship-vs-structure RAM

**Context.** TA-14's landing volume is "pad-frame offset <= `pad_radius_m`, |altitude above the pad plane| <= radius + 0.5" and the RAM exemption covers a ship *inside* that volume. A pad structure's collision sphere is centred on `pos` (the pad plane), so with any structure radius above 0.5 m a descending ship collides with the structure before it can enter the volume. TA-14 asked TA-19 to size `radius` to leave the column clear, which no radius above 0.5 m can do.

**Decision.** The exemption is the **approach column**: a not-DOCKED friendly ship whose pad-frame horizontal offset is <= `pad_radius_m` and whose altitude above the pad plane is >= -(radius + 0.5) is never RAM-tested against that pad's structure; the landing rule (6.4) takes over inside the volume, terrain and other structures still apply, and enemy ships still ram. Sim-lane code in TA-49 (one `Collision` predicate and a `test_collision.gd` row); TA-19 keeps its footprint and `pad_radius_m` work and inherits no sizing constraint. 03 s6.1 now says so.

## A-56 (TA-26) Bulk pose read on `SimView`

**Context.** `EntityViewPool.sync` reads `pos(id)` and `basis(id)` for up to 800 visible ids once per sim tick; each call re-checks liveness and builds a `Basis` from `fwd` / `up`. Measured p95 7.7 ms on tick frames against the 2.4 ms row (p50 1.1 ms between ticks), on a dev laptop with the planet drawn. Per-id typed calls through `SimView` cost ~2 x 4 us; a packed read removes the call and the per-id `Basis`.

**Decision.** Contract append (`[planned: TA-51]`): `func read_poses(ids: PackedInt32Array, pos: PackedVector3Array, rot: PackedVector4Array) -> int` on `SimView`. Semantics: for `i < ids.size()` writes `pos[i]` and `rot[i]` = the quaternion `(x, y, z, w)` of `basis(ids[i])` (`Basis(fwd x up, up, -fwd)`, the same frame `basis()` returns); dead or unknown ids write `Vector3.ZERO` and the identity quaternion; the caller sizes both arrays to `ids.size()` beforehand (S3: no allocation on read); returns the number of alive ids written. Results equal `pos(id)` / `basis(id).get_rotation_quaternion()` element-wise (TEST-02's contract test gains the row; NET-17's `NetSimView` implements it over the sampled mirror so `sync` stays one code path, 03 s10.1). TA-51 (sim, 0.5 d) adds it to `LocalSimView`; TA-52 (presentation, 0.5 d) switches `sync` to it and re-measures the 800-view case. If TA-52 still misses 2.4 ms, the next lever is TA-26's own: stagger the tick read across two frames; both are inside the row, which does not move (03 s10.2).
