## A-119 (CQ-1) Launch from a service pad: one thrust-hold rule for pilots and brains; the ascending contact is not a landing; the AUTO fuel gate is the brain's

**Evidence.**

1. **The rule exists in prose, twice, without numbers in a def.** 05 s2.5 (05:238): "Thrust >= 0.5 held for 0.3 s launches along the pad normal (`LAUNCHED`, `launch_speed_mps`) and aborts service at the current fill (partial fuel/ammo/repair kept; Ice already spent is not refunded)." 02 s2.3 (02:150): "a possessed ship may launch at any time with what it has, an AUTO ship waits until fuel >= 50 %." 05 s6.2 (05:574): the brain's DOCKED mode "wait for full service; serviced -> LAUNCH". ADR-09 (01:528) forbids the 0.5 / 0.3 / 50 % as code literals, which is exactly why PR #128 parks the ship: it could not add required def fields itself (10 s4.1 "Change").
2. **The Shipyard path is a different mechanism.** A-82 (2): a produced ship spawns DOCKED and the "normal B.5 `LAUNCHED` rule fires next tick, no hold timer"; `LaunchBay.step` launches every parked ship unconditionally (`launch_bay.gd:75-80`) because nothing is being serviced and no input is read. A service pad is the opposite: the ship stays until someone asks to leave. Both end in the same `LAUNCHED (ship, pad)` (04 s3.6 row 6) and the same A-87 clearing (`DOCKED` and `link` cleared in one tick; a flying ship never carries `link`).
3. **Brains drive input, not state.** 05 s2.3 / R0 B.5 tick order step 3: AI acts "writing input slots through `CommandSink.drive`"; step 4 `Docking.track(inputs)` already reads every input slot for the DOCK bit (D3 / D6). A thrust-hold rule read from the input slot therefore serves a human (holding thrust) and a brain (driving thrust 1.0 in LAUNCH mode) with one code path and no brain -> sim command. The 50 % fuel gate is a *decision* ("waits"), i.e. the brain's, and 02 s2.3 names it only for AUTO ships: it is an `autopilots.json` parameter, not a sim gate.
4. **The re-landing hazard is real and one-sided.** 03 s6.4 band: altitude above the pad surface <= `bounding_radius + 0.5`; `LAUNCHED` sets `vel = 5 m/s * up_pad`, so the ship stays inside the band for 3 ticks (0.167 m per tick at 30 Hz) while Collision keeps reporting a PAD contact; D1 would land it (v_vert <= 0 is "safe"). A ship *moving away from the pad* is never landing; a hovering ship at exactly zero vertical speed is.
5. **Hold state must be saved** (S4, D11), and `EntityStore.timer_b` is free for ships: PR #128 keeps the rearm line in `timer_a` and the repair share in `PadService`'s records; `timer_b` is used by ground units only (`ground_motion.gd:71`, braking hold) and 03:809 zeroes both timers at landing. Using it costs no FORMAT bump.

**Decision (binding; sim in GD-43, brains in AI-45).**

- **Launch rule (sim, step 10, `sim/docking/`).** A DOCKED ship whose `link` is a live service pad launches when the thrust of its input slot has been `>= flight_common.launch_thrust_min` (0.5) on every tick for `flight_common.launch_hold_s` (0.3 s; 9 ticks at 30 Hz, `ceil(hold_s * hz)`). The hold accumulates in the ship's `timer_b` (03 s3.2 row 33 gains "ship docked: launch hold s"), resets to 0 on any tick below the threshold, is zeroed at landing (03:809, already) and at `LAUNCHED`. No fuel, ammo, HP or service-state gate in the sim: "with what it has" (02:150). A ship on a `launch_pad: true` structure is `LaunchBay`'s and never enters this rule (D10 unchanged).
- **At `LAUNCHED`** (same tick): `DOCKED` and `LANDED` cleared, `link = 0` (A-87), `vel = launch_speed_mps * up_pad`, `rates = 0`, `timer_b = 0`; the service stay closes at its current fill (no refund, no `SERVICED` if incomplete; D9 unchanged); the pad is free (its queue head may land next tick; D6 unchanged); one `LAUNCHED (a ship, b pad)` with the row-6 payload. Nothing else is emitted. The saved-order resume on release is `ControlMachine`'s (05 s2.5 row 3) and unchanged.
- **Ascending contact (Touchdown D1 gains a clause).** A PAD contact whose ship moves away from the pad, `v.dot(up_pad) > 0` strictly, is not judged: no landing, no band, no hold. A ship at exactly zero vertical speed is judged as today. A pilot who cuts thrust after `LAUNCHED` falls back and lands again as an ordinary, graded landing (manual by D3). The own-team RAM exemption above the pad plane (A-109) already covers the departing ship.
- **Brain rule (sim_ai, AI-45).** 05 s6.2 DOCKED mode becomes: wait for `SERVICED`; if a service timer is paused (`ALERT WAITING_FOR_ICE / WAITING_FOR_ORE` for this ship) launch when `fuel01 >= landing.auto_launch_fuel01` (0.5) instead; then LAUNCH mode drives thrust 1.0, which satisfies the hold after 0.3 s. The Bomber's DOCKED mode launches only on an order (05 s2.5 row 3 "Bomber stays docked"; 01 s4.3 "never free-roams"). Every brain tags `AiTag.DOCKED` while waiting.
- **Def fields (B.1 append, OWNER).** `ships.json` `flight_common.launch_thrust_min` 0.5 and `launch_hold_s` 0.3, `_doc` "05 s2.5 Possess while DOCKED row; R0 B.24 A-119"; schema `required` extended, `minimum` 0 / `maximum` 1 and (0, 5]. `autopilots.json` per class `landing.auto_launch_fuel01` 0.5, `_doc` "02 s2.3 an AUTO ship waits until fuel >= 50 %; R0 B.24 A-119", in `ai13_autopilots.json` until the file exists.
- **Prediction (NET-18 note).** A DOCKED ship is not stepped (03:553); the launch is server-authoritative; the client holds the parked pose until wire flags bit 2 clears and `LAUNCHED` arrives. No prediction of the hold; a launch therefore feels one RTT late, which 05 s2.5's 0.3 s hold already hides at TARGET RTT.
- **Where.** **GD-43** (sim, Sonnet, 0.75 d, Opus review, M3, after GD-15), not GD-15: PR #128 is a 2.5 d task in Opus review with 2,006 tests, CQ-1 was raised as a question not a blocker, and the fields are a B.1 Change GD-15 could not land alone. **AI-45** (sim_ai, Sonnet, 0.5 d, M3, after GD-43 and AI-14) moves SC-17 / SC-18 from `LandingWorld` to real `Docking`. Until GD-43 lands, a ship landed on a service pad stays DOCKED (PR #128's interim).

**Not accepted:** a `Command.Kind` LAUNCH (an enum append for something the input slot already says; brains would need a second path); a launch on `SERVICED` in the sim (05 s2.5 row 3 wants the brain to decide; a possessed ship must be able to stay); a `dock_state` LAUNCHING grace period instead of the ascending skip (needs the pad id after `link` is cleared, which A-87 forbids; `LAUNCHING` stays unreported, see "Not ruled"); a fuel gate in the sim for AUTO ships (a decision, not physics; 02:150 scopes it to AUTO); a new saved array (`timer_b` is free and already serialised).

## A-120 (CQ-2) `flight_common.crash_pad_damage` 100, applied through `DamageSink`

**Evidence.** The rule is in three binding places: 02 s2.2 (02:138) "beyond, it is destroyed and the pad takes 100 damage", 03 s6.4 (03:802) and R0 B.5. Dropping it would delete design text the owner approved (O-2 / C1-04); keeping it without a def breaks ADR-09. The pad's damage goes where every other damage goes (GD-08 `DamageSink`), so the Core's integrated shield (GD-10) absorbs a crash on the Core pad exactly as it absorbs a bomb.

**Decision (OWNER, default applied).** `ships.json` `flight_common.crash_pad_damage` 100, required, `minimum` 0, `_doc` "02 s2.2 impact and landing: destroyed and the pad takes 100 damage; 03 s6.4; R0 B.5, B.24 A-120". On a CRASH outcome (D4 DESTROY band, or a DAMAGE band that empties the hull) `Touchdown` calls `DamageSink.damage(pad, crash_pad_damage, attacker = ship)` before the ship's `destroy`, so the HIT names the ship and shields apply. A crash on an own-team pad is the one case where a ship damages its own structure outside ramming (02 s4.3 rule 8's own-team exemption is a RAM-test rule, not a crash rule). Implemented in **GD-15** (PR #128 round 2; one field, one call, one test). Alternative: drop the rule from 02 / 03 / B.5 (not recommended; it is the only cost of a crash to the base and the HUD's "pad took damage" cue in 06 s7.1 relies on a HIT).

## A-123 (AI-44 review 1, 2) `TurretAim.slew(b, n, dir, turn_rad_s, dt, out)`; `right` re-projected onto the site tangent every slew tick; the 180 deg tie-break

**Evidence.** (1) A-118 says `n` is "appended", the AI-44 acceptance spells `slew(b, n, dir, turn_rad_s, dt, out)`, and PR #127 follows the acceptance; `TurretAim.slew` has one caller (`Ai17Kit.SlewDriver`, to be deleted by GD-09), so the position is free to choose and the acceptance's grouping (frame inputs first, output last) is the better signature. (2) A-118 (d) "right from `n`" intended tangency but gave no formula; `right = fwd.cross(up)` carried tick to tick is exact in real arithmetic and drifts in float32 (review: 1.8e-5 at 50k ticks, 4.5e-5 at 200k; a 30-minute match is 54k ticks). The 1e-5 invariant must be tick-count independent. The review also found that at exactly 180 deg `atan2` picks +-PI from the sign of a zero cross product, so the direction of turn is deterministic but unspecified.

**Decision (binding for AI-44 and GD-09).** (1) Signature **`static func slew(b: Basis, n: Vector3, dir: Vector3, turn_rad_s: float, dt: float, out: PilotInput) -> float`**; A-118's "appended" reads "added (second parameter)". (2) **Every slew tick ends with `right` re-projected onto the tangent plane**: `right = fwd.cross(n)`; if `right.length_squared()` is below the pole guard (the review's `is_zero_approx`, about 0.18 deg from the pole) keep the previous `right` with `right -= n * right.dot(n)`; `right = right.normalized()`; then `up = right.cross(fwd).normalized()`. `right.dot(n)` is then zero to float precision on every tick and never accumulates. GD-09 applies it in step 5 after the rotation; AI-44's `SlewSink` / `SlewDriver` apply the same in round 2 if open (otherwise GD-09 deletes them). (3) **Tie-break:** an azimuth error of exactly -PI maps to +PI (the turret turns left, the positive-yaw direction of A-118 (b)); the AI-44 test asserts `yaw == 1.0` again. Elevation is `atan2(fwd.dot(n), horizontal.length())` (well-conditioned; the review's nit), not `asin`.

**Not accepted:** leaving `right` unprojected with a looser invariant (the bound would depend on match length); re-projecting `fwd` instead (the muzzle is the state; `right` and `up` are derived, A-118 (d)); a `Basis.orthonormalized()` call alone (it does not know `n` and would keep the drift's roll).

## A-124 (CQ-4) Landings are detected in step 8 and resolved at the end of step 9; points stay in step 10

**Evidence.** R0 B.5 tick order (R0:330) and 03 s4.1 rule 7 (03:549) say "a landing detected in step 8 is graded and serviced in step 10"; 03 s6.4's heading says "evaluated in step 8, serviced in step 10". PR #128 resolves the detected contact at the end of step 9 (after Combat, before the deferred deaths) and records it in `sim/MODULE.md`. Reasons that hold: (a) a CRASH must die in the tick it crashes (03 s4.1 rule 6: deaths free slots after step 9 completes, so a destroy requested in step 10 would die a tick late and be rammed, shot or serviced in between); (b) a ship killed by Combat in step 9 must not land; (c) the x0.9 repair bonus and the hot flag read step 9's HIT (`last_damage_tick`), so the grade must follow Combat; (d) `DamageSink` (GD-08) is a step 9 facility. Nothing in 02 / 05 / 06 depends on the LANDING / DOCKED events being step 10's; 05 reads `dock_state` next tick either way.

**Decision.** The B.5 tick order reads: 8 "... ship vs terrain classification (destroy / damage / land / scrape) ..." (detection, unchanged); **9 "combat: weapon fire, damage rolls, flak bursts, shields, then landings resolved (`Touchdown`: band outcome through `DamageSink`, `LandingGrade` q and grade, LANDING then DOCKED), deaths (deferred free), wrecks"**; 10 "docking service ... scoring (points, GD-27)". 03 s4.1 rule 7 and the 03 s6.4 heading are patched to match; `LandingGrade` moves out of the step-10 parenthesis (its < 0.05 ms reservation stays on row 10, where the cost is accounted). No code change for PR #128.

## A-125 (CQ-5) `economy.json` `pad_queue_radius_m` 500, horizontal in the pad frame; the hold orbit is inside the zone

**Evidence.** A-33: `auto_dock_radius_m` (150) is a **horizontal** pad-frame distance for `Assist.auto_dock`; PR #128's D6 reuses it as a 3-D queue radius, which is a second meaning for one field. 05 s5.5 L2b (05:504, 05:512): a ship arriving at a busy pad holds "in a 400 m orbit at 150 m AGL until the pad is free" (`landing.hold_radius_m` 400, `hold_agl_m` 150 in `ai13_autopilots.json`); 01 s4.3 (01:226): pads "service docked ships in arrival order"; 03 s3.2 row `pad_queues` (03:451): "waiting ships in arrival order, <= 8 waiting per pad". With a 150 m zone no holding AI ship is ever queued, so arrival order is decided by whoever dives first, and the HUD's "pad busy, you are 2nd" (06 s7.1 service panel) is empty for the ships it is meant for. The zone must contain the hold orbit with a margin for orbit tracking (`approach_capture_deg` 30, `turn_cmd_max_deg` 60 give an overshoot of a few tens of metres at `hold_speed_mps` 50).

**Decision (OWNER, default applied).** `economy.json` gains required **`pad_queue_radius_m` 500** (`minimum` the largest `pad_radius_m`, `_doc` "05 s5.5 L2b 400 m hold orbit + 100 m tracking margin; 01 s4.3 arrival order; R0 B.24 A-125"). The queue zone is **horizontal in the pad's tangent frame** (A-33's frame), with **no altitude term**: a ship wishing for the pad (RETURN head order or DOCK held, D6) joins when its horizontal offset is <= `pad_queue_radius_m` and leaves when it exceeds it or drops the wish; arrival order is the order of entering the zone. A conservative 3-D prefilter (distance <= `sqrt(r^2 + ceiling_hard_m^2)`) is allowed as an implementation detail. `auto_dock_radius_m` keeps its A-33 meaning only. The brain's 25 s fuel-reserve divert (05:504) drops the wish and so the queue entry. **GD-15 round 2** (the queue is this PR's; one field, one distance). 05 s5.5's hold orbit must stay inside the zone: an `autopilots` schema `maximum` of `hold_radius_m` at 400 is AI-45's to add when `autopilots.json` is created, not ruled here.

**Not accepted:** keeping `auto_dock_radius_m` for the queue (two meanings, and the 05 L2b hold is outside it); a 3-D radius (a ship 450 m above its pad is queued or not depending on altitude, which the pilot cannot read); a per-structure field (one zone for every pad class; `pad_radius_m` already varies per class).

## A-126 (CQ-6) Rearm time scales with the most-missing slot

**Evidence.** 02 s2.3 (02:150): "Refuel time scales with fuel missing ... Repair time scales with HP missing", `rearm_time_s` in the table (Dart 6, Lancer 8, Bomber 10) with no scaling sentence; the cost sentence ("`rearm_ice` per round; gun rounds are free") is per round. The natural reading is the same law as its two neighbours: a full rearm from empty takes `rearm_time_s`, a top-up less. PR #128 runs one rearm line (`timer_a`, D7) rising at `1 / rearm_time_s` per second from the fill of the most-missing slot and loads every slot along it, so the time is `rearm_time_s x max(missing01 over primary ammo and the secondary count)` and the Ice is drawn per round as the line passes it.

**Decision.** Ratified: **rearm time = `rearm_time_s x max(missing share of primary ammo, missing share of the secondary load)`**, gun rounds counted for time (not cost), secondary rounds for both; an empty ship rearms in exactly `rearm_time_s` (02 s2.3 literal: Dart 180 ticks at 30 Hz). 02 s2.3 gains the sentence. Alternative (full `rearm_time_s` whenever anything is missing) rejected: it punishes the top-up landing that 01 s3.1.4 makes the core loop and contradicts the two neighbouring laws.

## A-127 `PadQueue.PER_PAD` = 8 is a structural table bound, ratified from 03 s3.2

**Evidence.** 03 s3.2 `pad_queues` row (03:451): "<= 8 waiting per pad" is the table's capacity, written as a bound of the saved SoA side table (like `InputSlots.ENTITY_SLOTS`), not a balance knob: no 02 row prices it, no doctrine or tier touches it, and 12 Pads + Core + Hangars per player make 8 waiters per pad a ceiling no 05 brain reaches (a Dart wing is 4-6). ADR-09 (01:528) governs sim-affecting *balance, caps, physics and tier values*; table capacities with a 03 source are the `const` pattern already used for slot counts.

**Decision.** `PadQueue.PER_PAD = 8` stays a `const` whose doc comment cites 03 s3.2 `pad_queues` and this row; a 9th wisher is not listed and D1 holds it until the queue shortens (no event). If S-SIM-1 or a soak shows a pad with 8 waiters, the number moves to `economy.json` as a required field by a one-row amendment; nothing else changes.
