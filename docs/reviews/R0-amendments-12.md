## A-99 The Core dome's radius and collapse length are def fields, not a derivation

**Evidence.**

1. 02 s5.1 (02:293) says "a dome over the Core's own footprint" and names three keys (`charge_max 2400, recharge_per_s 40, recharge_delay_s 5`); R0 B.7 (register line 239) fixes `integrated_shield {charge_max, recharge_per_s, recharge_delay_s}`; C3-05 (register line 120) adds nothing on size. No doc states a radius. The Shield Projector (02 s5.2, 02:311) carries `dome_radius` 250 and `collapse_s` 10 as def fields; the Core's block was written without them because its dome "over the footprint" was taken to be self-evident. It is not: a dome equal to the footprint cannot absorb anything.
2. Why the footprint is not enough (PR #102 "Interpretation choices" 1, verified by the Opus reviewer): `WorldDefs.radius_of` gives a structure the footprint half-diagonal as its collision sphere (Core 8 x 8 cells x 9.2039 m per cell = 52.07 m; `build_cell_m()` = `PLANET_RADIUS x pi / 2 / GRID_BUILD`). Collision (03 s4 step 8, 03:767) raises HIT when the sweep touches `radius + ProjectileDef.radius_m`; `ShieldDomes.absorb` (step 9, 03:537) takes a projectile whose sweep ends inside the dome. A dome at 52.07 m is entered one step after the HIT contact at 53.07 m fires, so it never absorbs. A dome must also cover every point from which a bomb's structure blast can still reach the footprint: 02 s4.3 rule 3 (02:230) damages "structures whose footprint edge is within 20 m" (`blast_radius_structure_m` 20, `projectiles.json`), so a bomb detonating 72.07 m from the Core's centre on the diagonal still damages it. Rockets (4 m) and siege shells (12 m) are inside that bound. 52.07 + 20 = **72.07 m** is therefore the smallest radius at which the sentence "absorbs bombs and rockets exactly like a Shield Projector" (02:293) holds for every absorbable shot that would have hurt the Core.
3. Why this is a def field and not a formula in code: ADR-09 (01:528) and CLAUDE.md ("every sim-affecting constant lives in JSON ... with a `_doc` citation"). The radius decides C-13 (02:1186) and BAL-31 (02 s18.3) and is tunable (a wider Core dome is a balance lever against bomb rushes that `charge_max` alone does not give); a derived quantity cannot be tuned without moving the footprint or every bomb's blast. `radius_of`'s own footprint derivation is marked "interim until Build sizes structures" (world_defs.gd:145), not a precedent. The cross-def coupling for `collapse_s` (the Core takes the maximum `shield.collapse_s` over all defs) makes the Core's collapse depend on a Projector def it does not reference; a modded or Doctrine-resolved Projector would change the Core. 02 s4.3 rule 6 (02:233) states "collapses to 0 for 10 s" for both dome kinds, so the Core's value is 10 and its citation is rule 6.
4. Required, not optional: 10 s4.1 lets a lane add "a new optional def field with a default" as an Append, but a default radius for the Core would be a float literal in `src/sim/**` (03:1239 forbids numbers outside `0.0, 0.5, 1.0, 2.0, -1.0`) or the very derivation this ruling removes. Exactly one shipped def (`core`) carries `integrated_shield`, so the migration is one entry. Required is the Change path (Architect proposes, owner approves) and this file is that proposal.

**Decision.**

1. **`integrated_shield` is `{charge_max, recharge_per_s, recharge_delay_s, dome_radius, collapse_s}`, all five required** (R0 B.7 line 239 appended; `structures.schema.json` and `towers.schema.json` `integrated_shield` gain `dome_radius` {number, 0..2000} and `collapse_s` {number, 0..120} in `properties` and `required`, the same bounds as the sibling `shield` block). The key names are those of the `shield` block (`dome_radius`, not `dome_radius_m`), so one reader serves both blocks; `shield.dome_radius` is already in metres by B.7 and 02 s5.2.
2. **Shipped Core values: `dome_radius` 75, `collapse_s` 10.** `collapse_s` 10 is 02 s4.3 rule 6 verbatim. `dome_radius` 75 is the 72.07 m bound of evidence (2) rounded up to the next 5 m: 2.93 m of margin so that TA-19's eventual structure sizing (`radius_of` "interim") or a +-1 cell footprint change cannot bring the collision sphere back ahead of the dome, and a round figure for the Core's HUD ring and `vfx_shield_dome` (07). The 2.93 m shell intercepts bombs that could not have damaged the Core; at 75 m that is < 8 % of the dome's cross-section and is accepted. **OWNER:** 75 (default applied) or the exact bound 72.07.
3. **Lower-bound rule (02 s5.1 appended):** a def's `integrated_shield.dome_radius` must be **>= footprint half-diagonal + the largest `blast_radius_structure_m` of any `shield_absorbed` projectile** (shipped: 52.07 + 20 = 72.07 m). The schema cannot check a cross-file bound; GD-10's unit test asserts it for every def that carries `integrated_shield`, and a reviewer of a def change to `core.footprint` or a `shield_absorbed` projectile's `blast_radius_structure_m` re-reads this sentence. No validator work is added (OWNER: a `validate_content.py` cross-check is a Haiku follow-up if the owner wants it mechanical; default: test only).
4. **Code consequences (GD-10, PR #102):** `ShieldTables._fill` reads `integrated_shield.dome_radius` and `collapse_s` exactly as it reads `shield.dome_radius` / `shield.collapse_s`; the half-diagonal + `reach` derivation, the `proj_collapse` maximum and the `b.get(..., default)` fallbacks for these two keys are deleted (a missing key is a validator error, not a runtime default); `sim/combat/MODULE.md` SH1 and SH3 name the def keys and drop the derivation text; the "needs content:" Open item is closed. The Core `_doc` string gains "dome_radius 75 (R0 B.18 A-99: >= half-diagonal 52.07 + bomb blast_radius_structure_m 20 = 72.07), collapse_s 10 (02 s4.3 rule 6)". C-13's scenario (`core_shield_dome.json`) re-records its event ticks if the 72.07 -> 75 change moves the entry tick; the acceptance (6 absorbed, collapse, 2 impacts, Core >= 600 HP) is unchanged.
5. **Not accepted:** ratifying the derivation as the rule (evidence (3)); optional keys with a code default (evidence (4)); `dome_radius_m` as the key name (the sibling block already fixed `dome_radius`); a `rules.json` or `match_rules.json` home (the radius is per def, like the Projector's); a Core dome equal to the footprint or the collision sphere (never absorbs, evidence (2)).

## A-100 "A dome covers a Core" (Exposure) is centre distance to any living Core, any team

**Evidence.** 02 s5.2 (02:311) "when the dome covers any Core after Core Exposure"; 02 s12.1 (02:858) "domes covering any Core get `exposure_charge_mult` 0.5 and `exposure_recharge_mult` 0.5". Neither defines "covers". The nearest existing geometric predicate between a structure and a radius is 02 s5.4 (02:322): "supplied when its footprint centre is inside the build radius of a connected node", a centre-in-disc test. Footprint overlap would need the Core's rotated 8 x 8 cell set against a sphere, a second geometry path for one Exposure flag. "Any Core" can only mean any team's: 02 s6.2 rules 3-4 (02:369-370) place a Projector inside a friendly build radius and outside every enemy build radius (600 m), while `shield.dome_radius` is 250 m, so a shipped Projector's dome can never contain an enemy Core's centre; the literal reading and the own-team reading are observably identical with shipped defs and the literal one needs no team test. Exposure's purpose (02 s13, 02:922: "finish stalemates") is to weaken the domes that make a Core unbombable, whoever owns them.

**Decision.** A Shield Projector's dome **covers a Core** when the centre of a living Core of **any team** is within `shield.dome_radius` of the Projector's position (centre distance; Cores are never under construction, so "living" = not destroyed). Recomputed when the structure set changes (`Economy.structure_epoch`), as PR #102 does. The Core's own integrated shield is not "a dome covering a Core" for this rule: at Exposure it is removed outright (02 s5.1, 02:857), never halved. 02 s5.2 gains this clause in the Shield Projector sentence; 02:858 is unchanged (it points at s5.2). PR #102's `_cover_flags` already implements this and needs no change; SH7 stands as written. **Not ruled:** nothing else in the PR's "Interpretation choices" is a contract matter; the Opus reviewer verified 2-5 against 02 (dice-free `damage_max`, Projector starts at 0 and the Core full, next-tick first test, start-outside / end-inside sweep) and they stay inside `sim/combat/MODULE.md`.
